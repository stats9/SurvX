# SurvX architecture, and what a second front end (Python) needs

SurvX has three layers. Keeping them separate is what lets a Python package share the numerical
work, the validation and the results of the R package.

| Layer | Where | What it does | Shared with Python |
| --- | --- | --- | --- |
| 1. Core | `src/survcore/*.hpp` | every estimator, likelihood, derivative, optimiser, variance, prediction | yes, unchanged |
| 2. C API | `src/survcore/survcore.h`, `src/capi.cpp`, `src/capi_par.cpp` | plain C functions: arrays in, arrays out, integer return codes | yes, unchanged (ctypes, cffi or pybind11) |
| 3. Front end | `src/rwrap.cpp`, `src/init.cpp` (the `.C` adapters) and `R/*.R` | formulas, data frames, S7 classes, printing, plots, help | rewritten in Python |

`dev/API_MAP.md` (generated by `python3 dev/api_map.py`) lists every `.C` entry point, the C API
function it wraps and the R files that call it. Rerun it after changing the wrappers; every
wrapper must have an R caller.

## Conventions of the C API

- Return value 0 on success; -1 null pointer or bad dimension, -2 non-finite or negative input,
  -3 no events of the requested type, -4 cannot be fitted or outside the support, -9 internal
  exception (caught; never thrown across the API).
- Matrices are row-major (`n x p` design matrices, `P x P` covariance matrices).
- Causes are coded 0 (censored), 1, ..., K. Clusters and strata are 0-based codes.
- Parameters are on the estimation scale (log, logit); the layout of each model is documented
  above its function in `survcore.h`. New parameters are appended (the constrained model with
  covariates of G_k), so that old layouts never change.
- Outputs are written only within the sizes documented in `survcore.h`; the R adapters allocate
  exactly these sizes, and `validation/memcheck` checks every entry point with these sizes under
  AddressSanitizer, UBSan and valgrind.
- `sc_fit_info` reports the log-likelihood at the start and at the end, the largest gradient
  component, iterations, convergence and flags (bit 1 iteration limit, 2 information not positive
  definite, 4 non-finite log-likelihood, 8 diverging parameter, 16/32 sum of incidences above one,
  64 constraint active).

## What the front end still does

All estimation, every interval, test, quantile, resample and fold assignment is computed by the
core. The headers added for this are `summaries.hpp` (distributions, quantiles as in R types 1 and
7, intervals, frailty summaries), `adjust.hpp` (propensity model, weights, weighted cumulative
incidence, bootstrap summaries, resampling, stratified folds), `interval_summary.hpp` (Turnbull
summaries, Finkelstein test, bootstrap bands), `phtest.hpp` (score tests of proportional hazards
and Holm adjustment), `timeeffects.hpp` (splitting of follow-up, time functions including the
natural spline basis of `splines::ns`, time-varying effects, cumulative predictions) and
`expand.hpp` (Fine-Gray data with delayed entry, merging of tied times, sandwich variance). Their
entry points are in `src/capi_support.cpp`.

Random draws (bootstrap resamples, permutations, cross-validation folds) are uniform indices
from one source (`draw_index` in `compare.hpp`). By default it is `splitmix64` started at the seed
argument of the call. A front end can install its own with `sc_set_index_source()`: the R wrappers
install `R_unif_index` for the duration of each call (`RStream` in `rwrap.cpp`, between
`GetRNGstate()` and `PutRNGstate()`), so R's `set.seed()` and `RNGkind()` govern every draw and a
resample equals `sample.int(n, n, TRUE)`. A Python front end can install a callback to
`numpy.random.Generator.integers` (or keep the splitmix64 default) in the same way.

The small computations on results are in the core too (`toolkit.hpp`, entry points in
`capi_support.cpp`): elementwise transforms (`sc_elementwise`: exp, log, logit, qnorm, ratios, p
values, signif and round as R, ...), sums and means as R computes them (`sc_reduce`, `sc_means`,
`sc_group_means`, `sc_cumsum_rows`), linear predictors and proportional-hazards predictions
(`sc_linpred`, `sc_ph_predict`, `sc_hazard_increments`), curves from counts (`sc_np_curve_inc`),
AIC, BIC and likelihood ratio tests (`sc_info_criteria`, `sc_lr_test`), Wald tables and standard
errors (`sc_wald_table`, `sc_se_diag`), residuals (`sc_hazard_residuals`, `sc_scaled_schoenfeld`)
and the grids of times (`sc_grid`: seq and pretty as R). In R they are reached through the helpers
`.sx_*` of `R/aac-core.R`.

What stays in the front end computes no result:

| Kind | Examples |
| --- | --- |
| model frames and design matrices | `Event()`, formula parsing, factors and contrasts, `strata()`, `cluster()` |
| bookkeeping | counting subjects and events for the printout, sizes of arrays, indices, the seed of each group |
| validation | whole-number checks of status and causes, argument checks |
| orchestration over core fits | loops of `model_scan`, `cv_compare`, bootstrap refits, the change point search of `time_effects()` |
| user-supplied functions | time functions given to `tt()` or `time_effects()` |
| printing | number formatting (`format`, `formatC`, `sprintf`), ordering of rows |
| plot layout | margins, panel grids, axis ranges and padding, text sizes |

## Tests that carry over

- `tests/testthat/` contains reference values computed by the core (coefficients, standard
  errors, log-likelihoods, predictions on deterministic data generated without random numbers
  where possible, such as `aft_data()` and `ck_data()`). A Python test suite can reuse them
  directly: the same core gives the same numbers.
- `validation/` compares SurvX with other R packages; `validation/memcheck` checks the core
  itself and needs no R.
